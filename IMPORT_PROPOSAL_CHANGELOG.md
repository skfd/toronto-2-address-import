| 2026-05-19 | §7 Checks: added `match_number_drift` (count now eight). Flags a MATCH/MATCH_FAR candidate when a different-numbered OSM address on the *same* street sits at least `slack_m` (default 2.0 m) closer to the candidate than the matched element — the MATCH-side counterpart of `nearby_street_mismatch`. Catches OSM positional drift: an old bulk import shifted by one or more houses, where the candidate still "matches" its same-numbered OSM twin but that twin is on the wrong building (e.g. city `164 Coleridge Ave` sits 1.7 m from OSM `166` while its matched OSM `164` is 5.7 m away). The check is informational — it never changes the verdict, since the address does exist in OSM and re-importing would create a duplicate; its job is to surface the drift for OSM-side cleanup. `slack_m` is deliberately small: OSM node-placement noise (~1–5 m) is comparable to a one-house drift gap on dense blocks, so a wider slack would miss most genuine drift. A back-scan of 410 uploaded runs found 576 candidates the check would flag across 99 runs, ~12 of them systemic clusters (Coleridge Ave, the "Fernway" streets in don-valley-village, Woodbine Ave) that were uploaded as duplicates with no drift flag shown to operators. |

| 2026-05-20 | POI filter now recognises lifecycle-qualified POI keys generically. Previously `POI_TAG_KEYS` in `t2/conflate.py` hardcoded only four lifecycle variants (`disused:shop`, `disused:amenity`, `disused:office`, `was:amenity`), so a closed or planned POI tagged with any other combination — `disused:tourism`, `abandoned:amenity`, the rarer suffix form `amenity:disused` — was treated as a *pure address node* and could MATCH an import candidate, silently suppressing a genuinely missing address. `_is_poi_node` now strips any of eleven OSM lifecycle qualifiers (`disused`, `abandoned`, `ruins`, `demolished`, `razed`, `removed`, `destroyed`, `construction`, `proposed`, `planned`, `was`) from either side of a tag key and checks the bare key against the eight base POI keys. Match-targets section reworded from "their `disused:*` / `was:*` variants" to "any lifecycle-qualified form, prefixed or suffixed". No tagging change; affects only which OSM nodes count as match targets vs. acknowledged POIs. |

| 2026-06-04 | Tile runs now ingest source addresses clipped to the tile **polygon**, not its bounding box. Adjacent tiles have overlapping bboxes but disjoint polygons, so the old bbox-only `candidates.ingest` pulled edge points into *both* neighbouring runs — the same civic address was reviewed twice (and only deduped late, at upload, by `osm_export.skip_cross_run_duplicates`). This makes the §Scope claim that the tiles "partition this boundary" true at ingest. Mechanism: `runs.polygon_json` (migration 016) carries the tile's `polygon_latlon`; `start_run` stores it, `ingest_stage` reads it, `candidates.ingest` keeps a bbox-prefiltered row only if `polygon.contains(point)` (strict, matching the `poly.contains()` test `tiles_build` already uses to count addresses). Wired through all run-creation entry points (`run_one_tile`, `run_for_all`, `spike_drive`, web `/runs/new` via a hidden `tile_id`); manual bbox-only runs leave `polygon_json` NULL and keep legacy behaviour. To preserve cross-tile matching for edge candidates, `osm_fetch.fetch` now pads its OSM clip bbox by `1.5 × match_radius_m` (`HALO_MARGIN`) — a candidate on the tile edge still sees OSM up to `match_radius_m` beyond the boundary; the halo is fetch-only (never persisted) and overlapping halos between tiles are harmless (OSM is read-only reference). No tagging or match-key change; affects only which source points belong to which run and how far the OSM search reaches. Existing (v1-DB) runs untouched. |
